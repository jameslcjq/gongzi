# 人员经费录入按钮注入速度分析

日期：2026-06-04

## 结论

当前不建议修改代码。

`人员经费录入` 按钮比 `自动额度匹配` 按钮出现得慢，主要是现有实现为了避免误注入，做了更严格的页面识别，并且在注入前读取人员经费核对表预填数据。这个慢属于当前安全策略和业务数据准备带来的正常差异，不是单纯的按钮渲染问题。

## 实际注入入口

一体化门户按钮注入由 `src/renderer/src/components/IntegratedPortalPage.vue` 中的 `installPortalAutomationScripts(...)` 统一触发。

该函数会在 webview 的以下事件中重复安装脚本：

- `dom-ready`
- `did-finish-load`
- `did-frame-finish-load`

安装时会对所有 portal frame 执行脚本，并在顶层 frame 再补执行一次。

相关代码位置：

- `src/renderer/src/components/IntegratedPortalPage.vue`
- `src/main/ipc/appApi.ts`

## 为什么自动额度匹配更快

`自动额度匹配` 对应脚本：

- `src/renderer/src/integration/salaryQuotaMatchScript.ts`

它的页面识别条件相对直接：

- URL 包含 `salSalaryAuditSCZF` 或 `/salaryGiveOut/`
- 页面已有工资发放相关表格字段
- 页面上存在精确的 `额度匹配` 按钮

只要满足这些条件之一，就可以确认是工资发放/生成支付相关页面。

脚本安装后会立刻执行一次 `injectButton()`，同时注册：

- `window.addEventListener('load', injectButton)`
- `setInterval(injectButton, 1500)`

所以只要目标按钮或工资表格字段已经出现，`自动额度匹配` 就能很快插入。

## 为什么人员经费录入更慢

`人员经费录入` 对应脚本：

- `src/renderer/src/integration/salaryPlanInputScript.ts`
- `src/renderer/src/integration/salaryPlanInput.user.js`

运行时实际注入的是 `salaryPlanInputScript.ts`，它会把 `salaryPlanInput.user.js` 作为 raw 脚本注入到一体化页面。

### 1. 页面识别更严格

人员经费录入必须判断当前页面确实是 `一般用款计划录入` 列表页。

它会检查：

- URL 是否匹配 `plan-web2/record/templateslist.html`
- 参数是否匹配已知菜单或视图编码
- 页面文字是否包含 `一般用款计划录入`
- 是否存在 `批量录入` 或 `更多`
- 是否存在列表提示文字，如 `待录入`、`指标文号`、`指标摘要`、`指标可用余额`、`部门预算经济分类`、`计划金额`
- 是否存在 `grid` 或 EasyUI datagrid
- 表格行中是否有 `cur_amt` 和 `dep_bgt_eco_code_name`

这些条件比额度匹配更严，必须等门户页面和表格渲染到比较完整的状态，按钮才会出现。

### 2. 有 400ms 防抖和 2 秒兜底轮询

人员经费脚本会：

- 初次执行 `boot()`
- 每 2 秒执行一次 `boot`
- 用 `MutationObserver` 监听页面变化
- 页面变化后通过 `setTimeout(boot, 400)` 防抖

这个设计可以避免 EasyUI 页面频繁变动时反复插入按钮，也避免之前出现过的自激循环和页面卡顿问题。

因此按钮出现会比“立即插入”的逻辑更保守。

### 3. 注入前会读取人员经费核对表

在 `IntegratedPortalPage.vue` 里，人员经费脚本生成前会先读取：

- 单位设置
- 人员经费核对表预填数据

对应调用：

- `window.salaryApi.getUnitSettings()`
- `window.salaryApi.getPersonnelExpensePlanPrefill({ archive: false })`

后端实现位于：

- `src/main/services/budget/personnelExpensePlanPrefill.ts`

该逻辑会扫描监控文件夹中的 Excel 文件，逐个探测是否是人员经费核对表：

- 列出根目录 `.xlsx` / `.xls`
- 跳过 `~$` 临时文件
- 对候选文件用 `XLSX.readFile(..., { sheetRows: 30 })` 探测表头
- 选中后再完整读取一次表格数据
- 再按单位设置过滤到当前单位

如果监控文件夹里 Excel 较多、文件较大、文件在网络盘，或存在正在被 Excel 占用的文件，这一步会拉长按钮注入前的等待时间。

### 4. 安装顺序上额度匹配也排在前面

`installPortalAutomationScripts(...)` 当前脚本顺序是：

1. 凭证按钮
2. 自动录入
3. 额度匹配
4. 人员经费录入

因此同一次 webview/frame 注入时，`额度匹配` 本身就会先于 `人员经费录入` 执行。

## 当前判断

`人员经费录入` 慢的原因可以归纳为四点：

1. 页面身份判断更严格，必须确认是 `一般用款计划录入` 列表页。
2. 必须等门户表格、按钮、字段渲染到足够完整，不能只看菜单文字。
3. 注入前会读取并解析人员经费核对表，涉及文件夹扫描和 Excel 读取。
4. 脚本安装顺序中，`额度匹配` 在 `人员经费录入` 前面。

这些都属于现有安全策略下的正常行为。保持当前实现可以降低误注入到首页、菜单页、错误标签页或未加载完成列表页的风险。

## 保持不改的理由

本次不改代码的理由：

- 当前差异可以解释清楚，不属于明显 bug。
- 人员经费录入涉及用款计划，误注入风险比按钮慢一点更值得避免。
- 现有逻辑已经有防抖和兜底轮询，偏稳妥。
- 如果为了提速提前插入按钮，可能重新引入误注入或页面卡顿风险。

因此本次结论是：只记录分析，不调整实现。
