# 工资系统维护手册

更新时间：2026-06-01

本手册用于约束长期维护方式。目标不是把项目变复杂，而是让以后改工资、报账、门户推送、授权和安装包时，有固定入口、有固定验证、有可追溯记录。

## 1. 仓库边界

正式仓库只认：

```text
E:\工资系统\gongzi
```

外层目录 `E:\工资系统` 只作为资料、临时文件、原始 Excel 和历史备份的工作区，不再作为 Git 仓库使用。

日常操作要求：

- 执行 `git status`、提交、推送时，工作目录必须是 `E:\工资系统\gongzi`。
- 开发和打包应用时，工作目录必须进入 `E:\工资系统\gongzi\app`。
- 不要把外层目录里的真实工资表、人员表、压缩包、Word 文档误放入正式仓库。
- 如果看到 `E:\工资系统` 下重新出现 `.git`，先停止提交，确认是否误初始化。

## 2. 目录分工

```text
gongzi/
  app/                       Electron 桌面应用
    src/main/                主进程、数据库、IPC、业务服务
    src/preload/             主进程和渲染进程之间的安全桥
    src/renderer/            Vue 界面、一体化门户注入脚本
    installer/               安装包图标、安装脚本、随包资源
    release/                 打包产物，本地生成，不提交
  docs/                      设计、接口、字段、维护文档
  scripts/                   辅助脚本
```

重点边界：

- 计算规则尽量放在 `app/src/main/services/`。
- 页面展示和用户操作尽量放在 `app/src/renderer/src/components/`。
- 一体化门户页面注入脚本放在 `app/src/renderer/src/integration/`。
- 前后端共享类型放在 `app/src/shared/types.ts`。
- 数据库结构放在 `app/src/main/db/` 和 `docs/sqlite-schema*.sql`。

## 3. 常用命令

PowerShell 中建议使用 `npm.cmd`，避免 Windows 下命令解析异常。

首次安装依赖或依赖变更后：

```powershell
cd E:\工资系统\gongzi\app
npm.cmd install
```

类型检查：

```powershell
cd E:\工资系统\gongzi\app
npm.cmd run typecheck
```

正式构建：

```powershell
cd E:\工资系统\gongzi\app
npm.cmd run build
```

打包安装程序：

```powershell
cd E:\工资系统\gongzi\app
npm.cmd run dist
Get-FileHash .\release\*.exe -Algorithm SHA256
```

发布前至少要跑：

```powershell
cd E:\工资系统\gongzi\app
npm.cmd run typecheck
npm.cmd run build
```

如果本次改动影响安装脚本、资源文件、正式包入口、授权文件或生产可见功能，还要跑 `npm.cmd run dist` 并记录安装包路径、时间和 SHA256。

## 4. 修改前检查

每次改代码前先看：

```powershell
cd E:\工资系统\gongzi
git status --short
```

处理原则：

- 工作树干净时再开始新的大改动。
- 如果有别人或上一次留下的改动，先确认它们是什么，不要直接覆盖。
- 只提交和本次任务有关的文件。
- 不要提交 `release/`、`dist/`、`dist-electron/`、`node_modules/`、真实 Excel、真实 Word、真实 PDF、压缩包。

## 5. 数据和隐私

程序运行数据默认在：

```text
D:\laojiu\gzdata
```

这里通常包含数据库、归档、导入导出文件和业务备份。它们属于本机业务数据，不属于源码。

仓库 `.gitignore` 已排除常见敏感文件，包括：

- `*.xls`
- `*.xlsx`
- `*.csv`
- `*.pdf`
- `*.doc`
- `*.docx`
- `*.zip`
- `*.rar`
- `*.7z`
- SQLite 数据库文件
- 构建产物和日志

以后如果确实需要把样例 Excel 放进仓库，只能放脱敏样例，并且要在 `.gitignore` 里对指定样例目录做白名单，例如 `tests/fixtures/`。不要为了提交一个样例文件而放开全局 Excel 忽略规则。

## 6. 发布流程

一次可靠发布应包含：

1. 确认工作目录是 `E:\工资系统\gongzi`。
2. `git status --short` 看本次改动范围。
3. 在 `app/` 下运行 `npm.cmd run typecheck`。
4. 在 `app/` 下运行 `npm.cmd run build`。
5. 如需交付安装包，运行 `npm.cmd run dist`。
6. 记录安装包路径、版本、生成时间、SHA256。
7. 确认正式安装包中一体化录制工具入口正常（2026-06-04 起正式包开放录制）；其它纯开发入口（如自动打开 DevTools）仍不应出现。
8. 用当前安装包做一次基本打开和关键流程冒烟测试。

发布记录建议写在提交说明或单独的发布记录中，至少包含：

```text
版本：
提交：
安装包：
SHA256：
验证命令：
重点验证功能：
已知问题：
```

## 7. 功能说明文档

需要补功能说明，而且应当和代码一起维护。

功能说明文档已建立：

```text
docs/feature-guide.md
```

每个功能按同一个模板写：

```text
功能名称：
入口位置：
面向用户：
解决什么事：
数据来源：
生成什么结果：
关键业务规则：
失败时会看到什么：
相关代码：
回归样例：
```

优先补这些功能：

- 登录、在线授权、离线授权。
- 单位设置、数据目录、备份恢复。
- 月度工资报账，包含工资表来源和一体化来源。
- 绩效工资。
- 年初调整。
- 保险凭证推送。
- 凭证合并和凭证导入。
- 自动录入。
- 一体化门户中的工资导入、补发导入、指标匹配、计划录入。
- 邮件附件下载。
- 工资年报和统计报表。

功能说明要写用户实际怎么用，不要只写代码结构。尤其要写清楚：

- 哪个按钮进入。
- 需要先准备哪些文件。
- 成功后会生成什么。
- 什么情况不能继续。
- 哪些结果需要人工核对。
- 哪些规则来自财政、人社、学校内部约定。

## 8. 代码注释规范

代码注释需要补，但不要满屏补。

应该加注释的地方：

- 业务规则不直观，例如凭证附件页数、当前月份限制、工资来源优先级。
- 一体化页面选择器和页面身份判断。
- 等待、重试、超时等数字有业务原因，例如保存后等待页面返回。
- Excel 字段映射、字段别名、金额口径。
- 数据库迁移、兼容旧数据、默认值补齐。
- 安全边界，例如授权缓存、离线授权、公钥校验、敏感数据过滤。

不建议加注释的地方：

- 代码已经一眼能看懂的赋值、循环、判断。
- 只是把函数名翻译成中文的注释。
- 已经过期的旧思路。
- 和当前代码不一致的“计划以后做”。

推荐格式：

```ts
// 业务规则：保险凭证按当前财政附件要求固定为 7 页，不能用工资凭证的动态页数。
```

如果规则来自外部文件、页面或人工确认，尽量写来源：

```ts
// 一体化页面规则：保存后会先停留在详情页，必须等待返回列表页后再处理下一条。
```

## 9. 脱敏回归数据

脱敏回归数据的目标是：以后改代码时，用一批固定样例跑一遍，知道核心业务有没有被改坏。

### 9.1 建议目录

当前已建立：

```text
tests/
  fixtures/
    README.md
    monthly-payroll/
    performance-payroll/
    voucher-push/
    insurance-push/
  expected/
    monthly-payroll/
    performance-payroll/
    voucher-push/
    insurance-push/
```

当前第一版样例使用 JSON 表达输入和预期结果，因此不需要放开 Excel 忽略规则。

如果后续要提交可直接导入的脱敏 Excel，需要只对白名单目录放开：

```gitignore
!tests/
!tests/fixtures/
!tests/fixtures/**/*.xlsx
!tests/fixtures/**/*.xls
!tests/expected/
!tests/expected/**/*.json
```

放开前必须确认样例已经彻底脱敏。

### 9.2 脱敏原则

不要直接把真实表格复制进仓库。推荐做法是“原始文件留在本地，脚本生成脱敏文件”。

字段处理建议：

| 数据类型 | 处理方式 |
|---|---|
| 姓名 | 改成 `教师A001`、`教师A002`、`退休A001` |
| 身份证号 | 换成明显虚构但格式稳定的测试号 |
| 手机号 | 换成 `13900000001` 这类测试号 |
| 银行卡号 | 换成测试号或只保留后四位 |
| 学校名称 | 可保留为测试学校，或统一成 `测试学校` |
| 工资金额 | 不使用真实金额，改成能覆盖计算规则的小金额 |
| 工号、人员编号 | 改成 `P0001`、`P0002` |
| 邮箱、账号 | 改成 `test001@example.com` |
| 备注 | 删除个人隐私，只保留测试场景说明 |

金额是否保留真实比例，要看测试目的：

- 测计算公式时，用人工设计的小金额，方便心算核对。
- 测导入列名和匹配时，金额可以很简单，重点覆盖字段变化。
- 测历史兼容时，保留旧格式结构，但内容全部替换。

### 9.3 样例覆盖

第一批样例不要贪多，建议先做 8 类：

1. 正常在职人员。
2. 退休人员。
3. 新进或调入人员。
4. 调出或停发人员。
5. 有补发人员。
6. 有扣款或个税人员。
7. 缺少匹配字段的异常人员。
8. 同名不同证件号人员。

月度工资至少覆盖：

- 工资表来源。
- 一体化来源。
- 当前月份允许处理。
- 历史月份禁止重新生成。
- 社保所属期覆盖当前月，且允许以前月份补缴记录。
- 个税所属期等于当前处理月份的上一个月。
- 报账预处理。
- 凭证和保险推送前的数据检查。

一体化门户至少覆盖：

- 正确页面才显示对应按钮。
- 页面按钮不重复。
- 缺参数时给出明确提示。
- 保存后能继续下一条。
- 页面选择器变化时能尽早失败。

### 9.4 预期结果

脱敏样例只有输入还不够，还要有预期结果。

建议每个样例同时保存：

```text
输入文件
预期 JSON
预期导出文件说明
人工核对清单
```

预期 JSON 示例：

```json
{
  "caseName": "monthly-payroll-basic",
  "expectedPeople": 4,
  "expectedVoucherCount": 2,
  "expectedInsuranceAttachmentPages": 7,
  "expectedWarnings": []
}
```

这样以后可以先人工核对，后续再逐步改成自动测试。

## 10. 回归测试清单

每次改核心业务前后，至少人工跑一遍相关清单。

月度工资：

- 能导入工资表。
- 能从一体化来源生成。
- 历史月份不能误重新生成。
- 社保文件不含当月所属期时必须拦截，含当月加补缴月份时应通过。
- 个税文件不是上月所属期时必须拦截。
- 报账预处理结果和预期一致。
- 工资凭证、保险凭证、附件页数符合规则。

绩效工资：

- 能识别人员。
- 能区分晋级、小档、退休、调出、新进、调入。
- 差额和备注正确。

一体化门户：

- 进入正确页面才显示功能按钮。
- 顶部没有重复按钮。
- 批量推送失败时能指出是哪一条。
- 保存后能继续下一条，不会卡住。

授权：

- 未授权不能进入正式功能。
- 在线授权成功后能进入。
- 离线授权校验失败时不能绕过。
- 换机器后硬件指纹逻辑符合预期。

打包：

- 安装包能生成。
- 安装后能打开。
- 数据目录不被覆盖。
- 一体化录制工具按策略保留在正式包；其它纯开发入口（如自动打开 DevTools）不出现在正式包。

## 11. 什么时候需要补文档

以下情况必须同步补文档：

- 新增一个用户可见功能。
- 改了工资、社保、个税、凭证、报账的业务口径。
- 改了一体化门户页面注入逻辑。
- 改了数据库表结构。
- 改了授权逻辑。
- 改了安装路径、数据目录、打包资源。
- 新增或变更脱敏回归样例。

维护项目最怕“代码改了，说明还是旧的”。以后只要用户操作步骤或业务结果变了，就把功能说明一起改掉。
